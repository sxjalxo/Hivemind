# Honeypot Intelligence Platform

An AI-assisted honeypot log analysis and threat intelligence frontend, inspired by
*"Beekeeper: Accelerating Honeypot Analysis With LLM-Driven Feedback"* (IEEE Access, 2025).

> **Turn raw honeypot telemetry into explainable attacker intelligence.**

The workflow the UI is built around:

```
Honeypot → Logs → Elasticsearch → AI/LLM Analysis → Attacker Behaviour Classification
        → MITRE ATT&CK Mapping → Threat Intelligence → Actionable Report
```

This repository contains **only the frontend**. It ships with a clearly-labelled demo
dataset so it runs standalone, and a single switch to move every request onto a
Python/FastAPI backend.

---

## Running it

```sh
npm install
npm run dev      # http://localhost:8080
```

Other scripts: `npm run build`, `npm run preview`, `npm run lint`, `npm run format`.

### Demo mode vs. the real backend

Demo mode is active whenever `VITE_API_BASE_URL` is **unset**. To point the app at FastAPI:

```sh
# .env
VITE_API_BASE_URL=http://localhost:8000
```

That one variable flips `DemoProvider → FastAPIProvider` in `src/services/index.ts`.
No component changes are required — every page consumes the `DataProvider` interface,
not a concrete implementation. The active provider is shown on the **Settings** page.

Demo data is isolated in `src/services/demo/` and never imported by the API path.
Every surface that renders it carries a **DEMO DATA** badge, so synthetic output is
never mistaken for a backend or model response.

## Evidence and provenance

Because this is a security tool rather than a dashboard, the UI never presents an LLM
label as a fact. Anything on screen is tagged with where it came from:

| Badge | Meaning |
| --- | --- |
| `OBSERVED` | Recorded directly in honeypot telemetry |
| `AI INFERENCE` | Generated by the LLM — shown with confidence and evidence |
| `CORRELATED` | Derived by correlating multiple sessions or sensors |
| `STATIC ANALYSIS` | Produced by inspecting a captured artefact |

Every AI conclusion — behaviour classification, suspicious indicator, ATT&CK mapping —
expands to the exact commands and log lines that produced it, with the source session
and timestamp. A technique is marked *observed* only when telemetry supports it.

Two conventions worth knowing when wiring the backend:

- **Confidence is a 0–1 fraction** (`0.94`), formatted for display by `formatPct`.
- **Risk score is 0–100** (`87`), rendered by `RiskScoreMeter`.

## Architecture

```
src/
  components/
    common/      RiskBadge, ProvenanceBadge, MitreBadge, Mono/Copy, KpiCard,
                 ConfidenceBar, Panel, loading/empty/error states
    charts/      ActivityTimeline, ClassificationDonut, RiskDistribution, palette
    layout/      AppShell, sidebar, top bar, global search, time range
    session/     SessionTimeline, LogViewer, AiAnalysisPanel, EvidenceList,
                 AnalysisProgress, LiveAnalysisPanel
    mitre/       MitreMatrix, TechniqueDrawer
    attacker/    AttackPatternGraph, SimilarityList
    report/      ReportView
    ui/          shadcn/ui primitives
  routes/        file-based routes (TanStack Start)
  services/      api, provider contract, demo + FastAPI implementations
  types/         API response types
  hooks/         useTimeRange, useAnalysisRun
  utils/         formatting, report export
```

Routing is **file-based** (TanStack Start): each file in `src/routes/` is a route and
`src/routeTree.gen.ts` is generated — don't edit it by hand.

### The provider contract

`src/services/provider.ts` defines the single `DataProvider` interface that both
implementations satisfy. Expected FastAPI endpoints:

```
GET    /api/honeypots
GET    /api/sessions              GET /api/sessions/{id}
GET    /api/sessions/{id}/timeline
GET    /api/sessions/{id}/events
GET    /api/logs
POST   /api/analyze/{session_id}
GET    /api/analysis  ·  GET /api/analysis/{id}
GET    /api/mitre
GET    /api/threat-intelligence
GET    /api/attackers/{ip}
GET    /api/reports   ·  POST /api/reports
GET    /api/status
GET    /api/dashboard
```

Log Explorer filters map onto ECS field names (`source.ip`, `event.action`,
`process.command_line`, `session.id`, `risk.score`, `mitre.technique`, …) so they
translate directly into Elasticsearch queries on the backend.

### Live analysis progress

`DataProvider.subscribeAnalysisProgress` is **optional**. `FastAPIProvider` deliberately
does not implement it yet — until the backend exposes a progress channel (e.g.
`WS /api/analyze/{session_id}/progress` emitting `AnalysisProgressEvent` frames), the UI
shows an indeterminate running state and says so, rather than animating invented
progress. Implementing that method lights up the stepper with no UI changes.

### Security boundaries

Elasticsearch and Ollama credentials never reach the browser. The frontend knows one
configurable API base URL; the backend owns the cluster, the index mapping and the model.
The LLM is not hardcoded anywhere — model name, analysis type and duration are read from
each backend response.

## Design system

Dark-only SOC theme defined entirely as oklch tokens in `src/styles.css`; components
never hardcode colours. Severity is a reserved scale (critical / high / medium / low /
informational) and is always paired with a text label, never colour alone.

Chart colours were validated with a colour-blindness and contrast checker against the
panel surface — lightness band, chroma floor, CVD separation and WCAG contrast. Tactic
hues are assigned to a tactic **permanently, never by rank**, so filtering never repaints
the remaining series. See the comments above the `--series-*` / `--tactic-*` tokens
before changing them.

Verified with no horizontal overflow at 414 / 768 / 1280 / 1600 px. Tables collapse to
cards on mobile; the terminal log viewer stays horizontally scrollable by design.
